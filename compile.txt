Compiling PtokaX on Unix
========================

    ./configure
    make
    sudo make install

`configure` probes for everything it needs and writes config.mk, which the
Makefile reads. Run `./configure --help` for the full option list.


Requirements
------------

    * GNU make
    * a C and C++ compiler (GCC or Clang)
    * Lua 5.1, 5.2, 5.3 or 5.4   (5.4 is preferred; see "Lua versions" below)
    * zlib
    * iconv  (part of glibc on Linux; a separate package on the BSDs and macOS)

Optional, for database support:

    * PostgreSQL, or MySQL/MariaDB, or SQLite

TinyXML and Skein are bundled in this source tree and are built automatically.
A system libtinyxml is not required -- see "TinyXML" below.

Database support
----------------

Pick at most one backend at configure time:

    ./configure --with-database=sqlite
    ./configure --with-database=postgres
    ./configure --with-database=mysql        (also MariaDB)
    ./configure --with-database=none         (the default)

IMPORTANT: the backend is not just a link-time addition. It changes the setting
ID numbering compiled into the hub (core/SettingIds.h and friends), so a binary
built with a database does not read a cfg/Settings.pxt written by one built
without it, or by one built with a different backend. Back up your config before
switching, and expect to re-check your settings afterwards.


Lua versions
------------

configure finds Lua by itself. It tries pkg-config first, over an ordered list
of the module names distributions actually use (lua5.4, lua-5.4, lua54, then
5.3, 5.2, 5.1, then a bare "lua"), and falls back to searching the usual include
and library directories.

Versioned module names are tried before the unqualified "lua", whose meaning
varies by system. configure warns if it ends up on anything newer than 5.4.

To pin a version:

    ./configure --with-lua=5.1

That is checked against the real LUA_VERSION_NUM in the headers, so it fails
loudly rather than silently building against a different release.

If your Lua lives somewhere unusual, bypass detection entirely:

    ./configure --with-lua-cflags=-I/opt/lua/include \
                --with-lua-libs='-L/opt/lua/lib -llua'


TinyXML
-------

The copy in tinyxml/ is built into the hub by default. TIXML_USE_STL switches
TiXmlNode's `value` member between std::string and TiXmlString, so it changes
the class layout, and every translation unit that includes <tinyxml.h> must
agree with the library. Building the bundled copy makes both sides agree.

To unbundle it, as distribution packagers usually must:

    ./configure --with-system-tinyxml

configure then link-tests the system library to determine which layout it was
compiled with, and matches it.


Skein
-----

The bundled Skein hash is built by default and is required for hashed passwords.
`--without-skein` makes HashPassword() a no-op that always returns false, and
the hub calls exit(EXIT_FAILURE) at startup if it reads an already-hashed
password from cfg/RegisteredUsers. configure warns if you ask for it.

skein/ ships Optimized_32bit and Optimized_64bit. Upstream ships identical C
sources in both (see skein/README/readme.txt); they differ only as slots for the
hand-written assembly in skein/Additional_Implementations, which this build does
not use. The build compiles Optimized_32bit.


Other useful options
--------------------

    ./configure --prefix=/opt/ptokax     install somewhere else (default /usr/local)
    ./configure --enable-debug           -O0 -g3 instead of -O2 -g
    CXXFLAGS='-O3 -march=native' ./configure     your flags win over the defaults
    make -j8                             parallel build
    make V=1                             show full compiler command lines
    make DESTDIR=/tmp/stage install      staged install, for packaging
    make help                            list targets and show the current config
    make config                          re-run configure with the same options
    make clean / make distclean          remove build output / also config.mk

Editing configure and running make re-runs it with the options it was last
given. Reconfiguring rebuilds everything, since the options change compile
flags.


Building outside the source tree
--------------------------------

Run configure from the directory you want the build in:

    mkdir build-sqlite && cd build-sqlite
    ../configure --with-database=sqlite
    make

config.mk, the objects and the binary all land in that directory, so several
configurations can coexist and the source tree stays clean.


Binding ports below 1024
------------------------

`make install` installs only the binary and deliberately does not touch file
capabilities. To let PtokaX bind a privileged port such as 411, run as root:

    make setcap

or, without capabilities:

    sysctl -w net.ipv4.ip_unprivileged_port_start=411

Neither is required if you run the hub on a port above 1024.


Config and data files
---------------------

PtokaX keeps cfg/, logs/, scripts/ and texts/ under the directory given with
-c, or $HOME/.PtokaX when run with -d, or the current directory otherwise. There
is no system-wide data directory, so `make install` does not install one. Seed a
config directory yourself:

    mkdir -p ~/.PtokaX/cfg
    cp -r cfg.example/* ~/.PtokaX/cfg/
    cp -r language      ~/.PtokaX/

The language/ directory has to go next to cfg/ for the Language setting to find
a translation.


Troubleshooting
---------------

If configure fails, config.log holds every test program it compiled along with
the compiler's output. That is almost always enough to see which header or
library is missing.

Compile guides for individual operating systems are in the PtokaX Wiki:
http://wiki.ptokax.org/doku.php?id=guides
